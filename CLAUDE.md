# CLAUDE.md

## Commands

```bash
# Development (auto-reloads via nodemon, sets NODE_ENV=dev)
npm run dev

# Production
npm run prod

# PM2 process management
npm run pm2:dev:start
npm run pm2:dev:reload
npm run pm2:logs

# Generate JWT secret and admin creation token for .env
npm run gen:secrets:helper

# Rebuild module-alias paths after adding new aliases
npm run update:alias

# Seed badges collection
npm run seed:badges

# Backfill portfolio media thumbnails (one-off, already run; --dry-run reports without writing)
node scripts/migratePortfolioMedia.js
```

There are no test or lint scripts defined. The entry point is `backend/server.js` (not root).

## Environment Setup

Copy `.env.example` to `.env` — the server loads a single `.env` file regardless of `NODE_ENV`. `NODE_ENV` (set by the npm scripts: `dev`, `prod`, `mobileapps`) still gates runtime behavior (see below). Required variables:

- `BASE_URL` — MongoDB connection string
- `JWT_SECRET` — use `npm run gen:secrets:helper` to generate
- `ADMIN_ACCESS_TOKEN` — generated by the same script
- `PORT` / `PORT_SOCKET` — HTTP and Socket.IO ports (default 8080)
- Bootstrap env vars (`BOOTSTRAP_ADMIN_EMAIL`, etc.) seed the initial admin/guest users on first DB connect

### NODE_ENV-gated behavior

Several code paths branch on environment; when debugging "works in dev, fails in prod" (or vice versa), check these:

- `userResponseUtil.js` — `otpInfo` is only included in auth responses when `NODE_ENV === "dev"`
- `stripeAccount.js` — `getAccountStatus` returns a fake "onboarding complete" when `STRIPE_ONBOARDING_BYPASS === "true"` (opt-in local shortcut; leave `false` when testing payments)

Stripe destination charges (`transfer_data.destination` + `application_fee_amount`) are **always on** — there is no environment gate. Every booking charge routes the business's share to their Connect Express account, so the business must have genuinely completed Stripe onboarding (test mode included — Stripe's hosted test onboarding activates the `transfers` capability). A booking against a non-onboarded business fails at PaymentIntent creation with "destination account needs … transfers".

## Architecture

### Request Flow

```
backend/server.js → securityMiddleware → i18n → routes → auth middleware → controller
```

`server.js` loads logging first (globally exposes `logger`), then registers module aliases, then mounts route groups. **`/api/v1/stripe` is mounted before `express.json()`** because the webhook needs the raw body for signature verification — don't move it below the JSON body parser. `textModerationMiddleware` runs on all JSON bodies after parsing.

| Prefix | Module |
|---|---|
| `/api/v1` | `backend/commonModules/routes` (auth, badges, categories, upload) |
| `/api/v1/app` | `backend/app/routes` (user-facing: home, users, services, packages, bookings) |
| `/api/v1/admin` | `backend/admin/routes` (admin panel, DB tools, language, users) |
| `/api/v1/stripe` | Stripe webhook (raw body) |

Swagger UI is served at `/api-docs` from `swagger/swagger_output.json`.

### Auth & Role Middleware

`authMiddleware.js` — verifies JWT from `Authorization: Bearer <token>`, looks up user in `userCache` (node-cache, 1 hr TTL) first, then MongoDB. Sets `req.user` (with `userType` flattened out of `accountState`) and sets i18n locale from `req.user.language`.

For business users it also sets `req.user.businessId` and `req.user.isAvailable` from the user's BusinessProfile. **`req.user.businessId` is the BusinessProfile `_id`, not the User `_id`** — booking/service documents store the BusinessProfile `_id` in their `business` field, so ownership checks must compare against `req.user.businessId`, never `req.user._id`.

`roleMiddleware.js` — factory that takes `allowedRoles[]` and checks `req.user.userType`. User types are: `user`, `business`, `admin`, `guest`.

### Response Pattern

All controllers use `sendResponse()` from `@utils/responseUtil`. Always pass a `translationKey` that maps to `backend/assets/locales/en.json`. Use `validateParams()` from the same module for request validation — it handles query params, path params, body fields, ObjectIds, dates, enums, and locations in one call.

### Aggregation Helpers

`backend/helperUtils/aggregationHelper.js` exports reusable MongoDB pipeline builders that controllers compose: `servicePipeline`, `packagePipeline`, `businessHelperPipeline`, `categoryPipeline`, `reviewRatingPipeline`, plus `paginationPipeline` (a `$facet` with metadata/data) and `finalRes` (unwraps the facet into `{ data, meta }`). List endpoints and the home controllers build `[{ $match }, ...entityPipeline, paginationPipeline]` rather than writing pipelines inline — extend the shared builders instead of duplicating stages.

The home endpoint (`homeController.js`) branches on `userType`: business users get bookings/stats/profile/Stripe onboarding status; customers get categories/businesses/services/bookings/events assembled from the same shared functions used by the individual list endpoints.

### Distances

Every distance the API reports is the same pair: the caller's `lat`/`lng` query params to one BusinessProfile's `location.coordinates`. Services, packages, promotions and bookings all borrow the business's location — none has one of its own.

Two layers produce it:

- **Straight-line, in the pipeline.** `haversineKmExpr` in `aggregationHelper.js` emits `distanceKm` in km, rounded to 1 decimal, on a 6371 km sphere. Free, computed per document, and it is what `nearestFirstStages` sorts on — that sort has to run before `paginationPipeline`, so it always uses the haversine value.
- **Road distance, after the query.** When `GOOGLE_MAPS_API_KEY` is set, `sendResponse` hands the outgoing payload to `attachRouteDistances` (`@utils/routeDistanceHelper`), which walks it for `distanceKm` nodes, batches the distinct business coordinates into one Google Routes `computeRouteMatrix` call per travel mode, and **overwrites `distanceKm`** with the lower of the driving and walking road distance, tagging it `distanceMode: "driving" | "walking"`.

Walking only competes within `ROUTE_WALKING_MAX_KM` (default 2). Pedestrian routes are nearly always the shorter of the two, so without that ceiling "lowest" would mean "walking" essentially always — Google returns a 178 km walking route from Lahore to Ludhiana across a border it refuses to give driving directions for.

A reported distance is always a real route; there is no straight-line mode on the wire. The three outcomes:

| Situation | Response |
|---|---|
| A driving and/or walking route exists | `distanceKm` = the shorter one, `distanceMode` set |
| Google answered for both modes, neither is usable (no drive route, walk beyond the cap) | `distanceKm` **removed** — same as any other "no distance to report" |
| Routing couldn't be reached (no key, quota, timeout) | haversine `distanceKm` left in place, **no** `distanceMode` |

That last row is deliberate: an outage must not blank every distance in the app, so an unlabelled `distanceKm` means "unverified straight line" and the distance is only dropped when Google positively answered for both modes. Results cache in Redis for 30 days under `routedist:{mode}:{origin}:{dest}`, with the origin rounded to 3 decimals (~110 m) so nearby callers share entries; a "no route exists" answer is cached but a transport failure never is.

### Shared Mongoose Schemas

`backend/models/Models.js` exports reusable sub-schemas: `locationSchema` (GeoJSON Point), `selectedBadgeSchema`, `breakIntervalSchema`, `dayScheduleSchema`, `slotIntervalSchema`, and `daySlotsSchema`. A day schedule (`BusinessProfile.operatingHours`) is `{ dayOfWeek, isOpen, startTime, endTime, breaks: [{ start, end }] }` — overnight is inferred when `endTime` < `startTime` (no flag), and breaks are rest windows inside the working window. Service/package `slots` use `daySlotsSchema` instead: discrete bookable intervals `{ dayOfWeek, isOpen, intervals: [{ open, close, isOvernight }] }`. Import these into model files rather than redefining them. Validation/generation share `buildDaySegments` from `@utils/serviceUtil`, which reduces a day to work segments (window minus breaks) in minutes.

Services/packages schedule in one of two modes, both storing the same intervals shape on `slots`: explicit intervals (validated to fit inside the operating hours, outside breaks, non-overlapping, only on open days; `sameAsBusinessHours` forced false, and `sessionSlotMins`/`gapBetweenSlotMins` stored as sent — whichever of the two is omitted is measured back from the intervals via `deriveSessionConfigFromSlots`, averaged when lengths or gaps vary), or `sameAsBusinessHours: true` + `sessionSlotMins`/`gapBetweenSlotMins` (intervals auto-generated from the business `operatingHours` via `generateWeeklySlots` and **stored**). Because business-hours intervals are materialized, every operating-hours update must call `regenerateBusinessHourSlots` from `@utils/serviceUtil` (userController and admin businessController already do) or the stored sessions go stale.

### Media Thumbnails

`backend/helperUtils/thumbnailHelper.js` generates a 400px WebP thumbnail for uploaded media and stores it beside the original as `<key>-thumb.webp` — images through sharp, videos through an ffmpeg frame grab (bundled binary, `FFMPEG_PATH` overrides), PDFs through a pdfjs render of page 1. sharp's prebuilt libvips has PDF input compiled out (`sharp.format.pdf.input.buffer === false`), which is why PDFs need pdfjs rather than another sharp call. That covers every type the upload filter accepts, so only media with no usable extension comes back without one. The name is a suffix rather than a `thumbs/` prefix on purpose: `cleanfiles` in `@utils/responseUtil` flattens any key containing a slash to its last segment, so a prefixed key would not survive a round trip through a request body.

`/api/v1/upload/s3` generates the thumbnail while the bytes are still in memory and returns `thumbnail`/`thumbnailUrl` alongside `file`/`fileUrl`. Portfolio writes pass their media through `attachThumbnails`: an entry that already carries a thumbnail key is stored as sent and costs nothing, since re-deriving it would mean a HEAD per item to confirm what the caller just said. Only an entry without one (a bare key, an older client, the migration replaying pre-thumbnail rows) falls back to `ensureThumbnail`, which HEADs the derived key and downloads + encodes only when it is genuinely missing. Generation failures degrade to a null thumbnail; they never fail the upload or the save.

`Portfolio.media` therefore stores `{ file, thumbnail }` rather than a bare key, and responses expose `{ url, media_type, thumbnail }`. The read pipeline still tolerates the old `[String]` rows (they return `thumbnail: null`), and update/delete deliberately hydrate only `business` so an unmigrated row can still be renamed or removed — `scripts/migratePortfolioMedia.js` backfills them.

### Caching Strategy

Two layers:
- **node-cache** (`@config/nodeCache`) — in-process, used specifically for authenticated user objects (`userCache`, 1 hr TTL)
- **Redis** (`@redisCache`) — distributed cache with gzip compression and optimistic locking. Use `cache({ namespace, params, ttl, fetchFn })` for read-through caching; use `invalidate(prefix)` to bust by namespace prefix on mutations.

### Socket.IO

`global.io` is set in `socketServer.js` and available everywhere. Event handlers live in `backend/config/sockets/`. Order-related socket events are in `orders/`.

### DB Bootstrap

On first MongoDB connection, `db.bootstrap.js` runs once (versioned by `BOOTSTRAP_VERSION` env var). It creates initial `AdminSettings` and seeds admin/guest users from env vars. Increment `BOOTSTRAP_VERSION` to re-run.
